# 確認事項一覧 ── 誰に何を確認するか

> あちこちに散っていた「確認が要るもの」を1箇所に集めたもの。出典は [ADR-001](adr/001-api-environment.md)、[運営ランブック](01-runbook.md)、[キックオフ台本](03-kickoff-script.md)。
> **Slack にそのまま貼る文面は末尾にあります。**

---

## まず結論

CTO に確認するのは **11 件**。うち **4 件が合宿全体をブロック**していて、**この4件が片付くまで開催日を決められません。**

| | 項目 | 誰が決める | 決まらないと |
| --- | --- | --- | --- |
| 🔴 1 | ADR-001 の承認（基盤の選定） | CTO | 何も始まらない |
| 🔴 2 | 既存 Organization で **API 利用が有効か** | Corp Eng | API が1回も叩けない |
| 🔴 3 | **API クレジットのチャージ**の道筋 | Corp Eng / 経理 | 同上 |
| 🔴 4 | 合宿用ワークスペース7個の新設可否 | CTO / Corp Eng | 費用上限とチーム別可視化の設計が決まらない |
| 🟡 5 | キー共有が社内ポリシー上OKか | CTO | キーの配り方が決まらない |
| 🟡 6 | ワークスペース作成権限の委譲 | Corp Eng | 準備のリードタイムが読めない |
| 🟡 7 | 座席の追加（単価・リードタイム・合宿後） | Corp Eng | 参加者名簿の確定期限が決まらない |
| 🟡 8 | サンドボックス（Slack / GitHub）の用意 | Corp Eng / 開発基盤 | 副作用ありのお題が出せない |
| 🟢 9 | 社内の実データを題材にしてよいか | 情シス / セキュリティ | 当日 Q&A で答えられない |
| 🟢 10 | 成果物を合宿後どうするか | CTO | 参加者のモチベーションに直結 |
| 🔴 11 | 上記から逆算して**開催日をいつに置けるか** | CTO | 準備が着手できない |

🔴 = 全体をブロック ／ 🟡 = 準備の段取りが決まらない ／ 🟢 = 当日までに決まればよい

## 1. ADR-001 の承認 ── 基盤をどれにするか　🔴

**聞くこと:** [ADR-001](adr/001-api-environment.md) を承認してほしい。決定者の欄が空のままになっている。

**中身:** 既存の Claude Organization 配下に、合宿用のワークスペースをチーム数ぶん用意する（＝ Anthropic API 直）。

**なぜこの案か:**

| 選択肢 | 却下理由 |
| --- | --- |
| Claude Platform on AWS | IAM 設計と `ANTHROPIC_AWS_WORKSPACE_ID` の配布が要る。**6チーム・2日間では、削減できる管理コストより構築コストのほうが大きい** |
| Amazon Bedrock | 機能が部分集合（Managed Agents 非対応）。モデルアクセス有効化とクォータ引き上げにリードタイム |
| 参加者が個人で購入して経費精算 | **会社は既に法人テナントへ移行済み。**個人契約に戻すのは意思決定に反する |

> ⚠️ [運営ランブック §2](01-runbook.md) は 2026-08-19 時点で Claude Platform on AWS を推奨していたが、**ADR-001（08-26）でこの規模には API 直と結論を変えている。**古いほうを見せると話が混乱するので、ADR を正とする。

**決まらないと:** 以降すべてが止まる。

---

## 2. 既存 Organization で API 利用が有効になっているか　🔴 最重要

**聞くこと:** Claude Console（API）の利用が、既存 Organization で有効になっているか。

**なぜ聞くのか ── ここがいちばん誤解されやすい:**

> **Claude Team / Max（座席課金・claude.ai）と API（従量課金・Console）は財布が別。**
> エンジニアリング用テナントが整備され、全員が Max 座席を持っていても、**それは API が使えることを意味しない。**
> 座席は claude.ai と Claude Code のためのもので、`messages.create()` を叩くには別途 API クレジットが要る。

**決まらないと:** テンプレートが1回も動かない。合宿が成立しない。

---

## 3. API クレジットのチャージの道筋　🔴

**聞くこと:** $300 のチャージを、誰がどのフローで行うか。稟議は要るか。リードタイムは。

**金額の根拠**（テンプレートの実測ベース）:

| | 計算 | 金額 |
| --- | --- | --- |
| エージェント実行 1回 | 実測 3〜5周 | $0.03〜0.10（平均 $0.06） |
| 1チーム2日間で 500 回 | 500 × $0.06 | $30 |
| 6チーム分 | | **$110〜180** |
| **チャージ額** | 余裕込み | **$300** |

> 座席が用意できない人に Claude Code を API キーで動かす場合（→ 7）は、**1人1日 $20〜50** と1桁多い。2人以上なら **$500 に増額**。

**決まらないと:** 2 と同じ。

---

## 4. 合宿用ワークスペース7個を一時的に作ってよいか　🔴

**聞くこと:** 「Organization 配下は Corp Eng が統一的に管理」という方針に対し、**2日間の一時的なワークスペースを7個**（6チーム＋運営）作ることが認められるか。命名規則や棚卸しルールなど従うべき既定はあるか。

**なぜ分けるのか:**

- **費用の上限をワークスペース単位の spend limit で技術的に強制できる**（各 $50）
- チーム別の使用量が集計でき、講評の材料になる
- 運営用を1つ分けるのは、**サンプル作成や当日のトラブルシュートがチームのコスト比較を汚さないため**
- 合宿後にワークスペースごと畳めるので、継続管理の負担が残らない

**認められなかった場合の代替:**

| 代替案 | トレードオフ |
| --- | --- |
| 既存ワークスペースを1つ借りて、期間中だけ spend limit を設定 | チーム別の可視化ができない |
| 2〜3 ワークスペースを複数チームで共用 | 上限の粒度が粗くなる |

## 5. チーム内での API キー共有が社内ポリシー上OKか　🟡

**聞くこと:** 1チーム（3〜4名）で1本の API キーを共有する形が、社内規定上認められるか。キーの発行単位（個人 / チーム / システム）に既定があるか。

**Anthropic の規約側は問題なしと読める**（2026-08-26 時点の公開版を確認）:

- 契約主体は「組織」であって個人ではない
- 使用制限が禁じているのは競合製品の構築・リバースエンジニアリング・再販。社員間の共有への言及はない
- *"Customer is responsible for all activity under its account."* — 組織が全活動の責任を負う建て付けで、個人ごとの credential を要求していない

> **Claude Team / Pro とは製品が違う。**あちらは座席課金なので1座席の共有は想定外だが、**API は従量課金で、キーは座席ではなくインフラの認証情報。**同じ直感を持ち込むと判断を誤る。

> ただし「組織が全活動の責任を負う」以上、**誰が何をしたか追えないこと自体がガバナンス上の弱点**になる。
> **チームごとにワークスペースを分ける案は、規約回避ではなく責任範囲を追跡可能な単位に絞るための設計**として説明する。

※ これは公開規約を読んだ結果であって法務判断ではない。正式な確認が要るなら法務へ。

---

## 6. ワークスペース作成権限とキー発行を運営に委譲できるか　🟡

**聞くこと:** 運営がワークスペースを作りキーを発行できるか。できない場合、Corp Eng に代行を依頼する手順とリードタイムは。

**決まらないと:** D-14 の準備がいつ着手できるか読めない。

---

## 7. 座席の追加 ── 単価・リードタイム・合宿後の扱い　🟡

**聞くこと:**

- 法人テナントの座席の**単価**（API クレジットとは別の財布なので予算も別に立てる）
- 座席追加の**リードタイム**
- 合宿後も継続して使うのか、期間後に外すのか

**なぜ必要か:** 全員が法人テナントの座席を持っているとは限らない。

| 参加者の状態 | 対応 |
| --- | --- |
| 法人テナントの座席あり | 対応不要 |
| **個人の Pro / Max で利用中** | 合宿期間中は法人テナントの座席を使ってもらう |
| **Claude 未利用（ニューカマー含む）** | 座席を追加。事前に軽く触ってもらう |
| 座席が用意できなかった | API キーで Claude Code を動かす（$20〜50 / 人日、要 専用ワークスペース） |

> **個人プランのまま業務に使うのは避ける。**合宿の題材によっては社内資料を扱うので、**社内データの通り道が個人契約になる**のは法人テナントへ移行した意思決定に反する。

> ニューカマーは通常のジョイン申請で座席に入る見込みなので特別な手配は不要。**ただし申請が合宿に間に合うかだけは逆算して確認する。**

**決まらないと:** 参加者名簿と座席の突き合わせをいつまでに終えるべきかが決まらない。

---

## 8. サンドボックス（検証用 Slack / GitHub Org）を用意できるか　🟡

**聞くこと:** 書き込み先として使える検証用の Slack ワークスペースと GitHub Organization を用意できるか。既にあるなら参加者に権限を渡せるか。

**なぜ必要か:**

> 本番の Slack や GitHub に向けたままエージェントのループを回すと、**止める前に数十件〜数百件の書き込みが飛ぶ。**
> これは腕の問題ではなく、ほぼ前提として起きる。

**決まらないと:** 「副作用あり」のお題（チケット起票・通知・申請の代行）を出せない。読むだけのお題に寄せることになり、**全チームが似たものを作る**。

---

## 9. 社内の実データを合宿の題材に使ってよいか　🟢

**聞くこと:** 社内の実データ（Wiki、議事録、Slack ログ、コード）を題材にしてよいか。よい場合、どこまでか。

**振り先:** 情報システム部 / セキュリティ。**CTO にはルーティングだけお願いする。**

**決まらないと:** キックオフのQ&Aで答えられない。**曖昧なまま当日を迎えると、質問された瞬間に信頼を失う。**ダメならダミーデータのみで回す（テンプレートには `workspace/docs/` にダミー資料が入っている）。

**期限:** D-7。

---

## 10. 成果物を合宿後どうするか　🟢

**聞くこと:** 作ったものを実運用に載せる道があるか。あるならその窓口は。

**なぜ必要か:** 参加者に必ず聞かれる。「作って終わり」と分かっていると発表の熱が落ちる。**逆に「良いものは載せる」と言えるなら、それ自体がいちばん効く動機付けになる。**

**期限:** D-7。

---

## 11. 開催日をいつに置けるか　🔴

**聞くこと:** 1〜8 の承認とリードタイムから逆算して、開催日をいつに置けるか。

**逆算に必要な数字:**

| 何のリードタイム | 誰に聞く |
| --- | --- |
| API 有効化 / クレジットのチャージ | Corp Eng・経理 |
| ワークスペース新設の承認 | CTO・Corp Eng |
| 座席追加 | Corp Eng |
| サンドボックスの用意 | Corp Eng / 開発基盤 |

これが出れば D-28 / D-21 / D-14 / D-7 のチェックリスト（[運営ランブック §3](01-runbook.md)）に日付を入れられる。

## CTO ではなく、別の人に聞くもの

| 相手 | 内容 |
| --- | --- |
| **法務** | キー共有についての規約解釈の正式確認（必要なら。→ 5） |
| **経理** | $300 のチャージ ＋ 座席追加の予算計上と支払方法 |
| **情シス / セキュリティ** | 社内データを外部 LLM に投げる可否（→ 9） |
| **各チームの EM** | ニューカマーの座席申請が合宿に間に合うか（→ 7） |
| **運営（自分たち）** | 参加者名簿と座席の有無の突き合わせ。チーム分け |
