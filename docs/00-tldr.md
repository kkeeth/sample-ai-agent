# これだけ ── AIエージェントの要点

> 事前に読むページ．5分程度で読めます．

---

## 1. エージェントの本体は30行のループ

新しい技術はほとんどなく，中でやっているのはこれだけです．

```
① モデルに送る    …… 依頼 ＋ ツールの一覧 ＋ これまでの全履歴
② モデルが返す    …… 「このツールを、この引数で呼べ」
③ あなたが実行する …… ただの関数を呼ぶだけ
④ 結果を履歴に足して ① に戻る
   モデルが「もう終わり」と言ったら抜ける
```

このループはすでに `src/agent.ts` に書いてあります．

---

## 2. モデルは関数を実行しない

```mermaid
flowchart LR
    Model["モデル<br/>次の一手を決めるだけ"]
    Loop["あなたのループ<br/>src/agent.ts"]
    Tools["ツール<br/>ただの関数"]

    Loop -->|"依頼 ＋ ツールの一覧 ＋ 全履歴"| Model
    Model -->|"このツールをこの引数で呼べ"| Loop
    Loop -->|"実行"| Tools
    Tools -->|"戻り値"| Loop
```

モデルとツールの間に線がありません． モデルは「呼べ」と言うだけで，実際に呼ぶのは我々が書いたコードです．

なので「AI が勝手に何かする」ことは原理的に起きません．危ないツールを渡さなければ何も起きないし，実行前に人間の確認を挟むことも可能です．

---

## 3. モデルは毎回記憶を失う

ループは毎回これまでの全部を送り直しています．

```
1周目   [依頼]
2周目   [依頼][指示①][報告①]
3周目   [依頼][指示①][報告①][指示②][報告②（ファイル全文）]
        └───── 3周目は、この全部を毎回送っている ─────┘
```

会話が伸びているのではなく，まるごと再送しています．

ツールの戻り値にファイル全文を詰めると，それ以降の全周回でその全文を送り続けることになります．「戻り値は必要な分だけ返す」 これがコストにも精度にも効くところです．

---

## 4. description はコメントではなくプロンプトの一部

いちばんよくある詰まり方は「モデルがツールを呼んでくれない」というものです．

モデルはツールの説明文しか読んでいなく，実装は見えていません．
| 判定  |  description  |
| --- | --- |
| BAD | `ファイルを読む` |
| GOOD | `社内資料の中身を返す。パスが分からないときは、先に list_files か search_files を使うこと` |

「何をするか」だけでなく「いつ使うか」まで記述する．呼ばれないときは，まず説明文を疑ってみてください．

---

## 5. 合宿で書くのは1ファイルだけ

`src/tools.ts` に3つ書きます．エージェントの中身は実質この3つで全部です．

| | 何を書くか |
| --- | --- |
| `SYSTEM_PROMPT` | 役割と，守ってほしい方針 |
| `tools` | ツールの一覧 |
| `runTool` | ツールの中身．ただの関数． |

ループ・コスト計測・承認ゲート・安全装置は用意してありますが，必要あれば適宜変更してください．

書き方に詰まったら，参考例もあります．丸ごとコピーして始めてOKです．

```bash
cp examples/doc-agent/tools.ts   src/tools.ts   # ローカルのファイルを読む
cp examples/http-agent/tools.ts  src/tools.ts   # HTTP を叩く
cp examples/state-agent/tools.ts src/tools.ts   # 状態を書き換える
```

---

## 6. 作業量の8割は、普通のプログラミング

| 工程 | 中身 |
| --- | --- |
| 何を自動化するか決める | 「誰の、どの手作業か」まで具体化する |
| どんなツールが要るか決める | 3〜5個に絞る。**設計の本体はここ** |
| **ツールの中身を実装** | ただの関数．API 叩く，DB 叩く，ファイル読む |
| システムプロンプトを書く | 役割と方針 |
| **回して直す** | 説明文とプロンプトを詰める |

※時間は適当です．

新しいスキルなのは最後の「回して直す」だけです．

---

## 7. もし詰まったら

| 症状 | まず疑うところ |
| --- | --- |
| ツールを呼んでくれない | `description`。「いつ使うか」が書いてあるか |
| 同じツールを何周も呼び続ける | 戻り値。空か、エラーか、次に何をすべきか書いてないか |
| 変な引数を渡してくる | `input_schema` の `description`。例を書く |
| 遅い・高い | ツールが多すぎないか。戻り値が長すぎないか |
| 何も分からない | `-v` を付けて実行する。考えていることが見える |

**それでも詰まったら，ツールを減らしてください．** 5個で動かなくても，2個なら動くことが多いです．

## 最初の一歩

```bash
# サンプルは bun で用意しましたが適宜お好きな環境を使ってください
bun install
cp env.example .env    # 運営から配られたキーを貼る
bun run check          # 疎通確認
bun run agent "今日は何日?" -v
```
