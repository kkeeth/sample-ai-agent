## 背景

開発合宿で「AIエージェントを作る」をテーマにする。

### 先に: そもそも API 環境は要るのか

「エンジニアは全員 Claude Max 座席を持っていて、Claude Code も動いている。なぜ追加の環境が要るのか」。これが最初に来る問いだと想定している。先に答える。

**要る。ただし「Claude を使うため」ではなく「合宿の学習目標のため」である。**

この合宿のゴールは「Claude を使えるようになる」ことではない。**「エージェントの中身がただのループだと分かる」こと**である（→ [これだけ](../00-tldr.md)）。

| やり方 | 参加者の体験 | 追加費用 | 学習目標 |
| --- | --- | --- | --- |
| Claude Code をそのまま使う | 完成品のエージェントを**使う** | $0（座席済み） | ❌ 中身は見えない |
| Claude Agent SDK で組む | Claude Code のハーネスを**借りて**組む | $0〜（→ 案0） | △ ループは SDK の中 |
| **Messages API を直接叩く** | ループを自分で読む・回す | **API クレジットが要る** | ⭕️ **これが目標** |

`src/agent.ts` の30行が示すこと（毎回まるごと送り直している／モデルは関数を実行しない）は、**生の `messages.create()` を叩いて初めて見える**。ハーネスに包むと、その30行はライブラリの中に隠れる。

**つまり API クレジットは、Claude を使う費用ではなく、教材を成立させる費用である。** 6チーム2日間で $110〜180（実測ベース。→ 費用の根拠）。

> **「座席があるじゃないか」への短い答え。** 座席は claude.ai と Claude Code のためのもので、参加者が書いたプログラムから `messages.create()` を叩くための認証ではない。**財布が別**であり、座席を何席持っていても API クレジットは増えない（→ 論点1）。

学習目標そのものへの異論はありうる（「使えれば十分では」）。その場合は **案0** を採ることになり、本 ADR の残りはすべて不要になる。**議論すべきはそこであって、API が要るかどうかではない。**

### 次に: 叩くとして、どこ経由か

「使うなら AWS 経由では」という問いには **案4** で答えている。結論だけ先に書く。**トークン単価は変わらない。** 得られるのは請求と権限の一元化であって価格ではなく、この規模（6チーム・2日間）では削減できる管理コストより構築コストのほうが大きい。**合宿後の恒常運用なら有力。**

### 前提条件

| 項目 | 想定 |
| --- | --- |
| 参加人数 | 最大 25 名 |
| チーム数 | 5〜6 チーム（1チーム 3〜4 名） |
| 期間 | 2 日間 |
| 使用モデル | `claude-opus-5`（全チーム共通） |

### すでにある社内環境

CTO の発言より:

> カミナシでは複数の Claude Team テナントを1つの Claude Organization 配下で運用していますが、Organization 配下のすべての Team 設定は、Corp Eng によってカミナシのセキュリティ & ガバナンスポリシーや将来の継続管理可能性を考慮しつつ、統一的に管理しています

つまり **Claude Organization は既に存在し、その配下は Corp Eng が統一管理している**。

さらに現場の実態として、以下が確認できている。

| 項目 | 状況 |
| --- | --- |
| 法人テナント | **エンジニアリング用テナントが用意済み** |
| 従来の運用 | 個人が Claude Max を契約し、経費精算していた |
| 現在 | **法人テナントへの移行が完了済み**。既存ユーザーはログイン時にリダイレクトされ、SSO でサインインする |
| 認証 | 会社ドメインを入力 →「Continue with SSO」 |
| 利用実態 | **エンジニアのほとんどが Claude Max で Claude Code を使っている** |

**会社は既に「個人購入＋経費精算」モデルを卒業している。** この事実は選択肢の評価に直接影響する（→ 案3）。

したがって本 ADR は「新しく組織アカウントを作る」話ではなく、**既存 Organization の配下に合宿用の器をどう置かせてもらうか**という話になる。実行には Corp Eng の関与が必須。

> ⚠️ **Claude Team と API の課金は別系統である点に注意。**
> Claude Team は claude.ai を使うための**座席課金**、API（Console / クレジット）は**従量課金**で、財布が分かれている。Team テナントが整備されていても、**API 利用が有効になっているとは限らない**。ここは確認が必要（→ 未解決の論点1）。

### 満たしたい要件

1. **全チームが同じモデル・同じ環境で動く** — 環境差ではなく設計の差だけが成果に現れるようにしたい
2. **費用に上限をかけられる** — 暴走したチームがあっても被害が限定される
3. **チーム別に使用量が見える** — 講評やふりかえりの材料にしたい
4. **準備と後片付けの手間が小さい** — 2日間のイベントに見合う範囲で
5. **社内データの通り道が会社の管理下にある**

## 決定

**既存の Claude Organization 配下に、Corp Eng の管理下で合宿用のワークスペースをチーム数ぶん用意する。**

新規に組織を立てることはしない。既存のガバナンス体制に乗せる。

```
既存の Claude Organization（Corp Eng 管理）
└── 合宿用（API クレジット $300 をチャージ）
    ├── workspace: team-a   → API キー / spend limit $50
    ├── workspace: team-b   → API キー / spend limit $50
    ├── workspace: team-c   → API キー / spend limit $50
    ├── workspace: team-d   → API キー / spend limit $50
    ├── workspace: team-e   → API キー / spend limit $50
    ├── workspace: team-f   → API キー / spend limit $50
    └── workspace: 運営      → API キー / spend limit $50
```

### 運営用ワークスペースが必要な理由

チーム分とは別に、運営用を1つ用意する。用途は4つ。

| 用途 | いつ |
| --- | --- |
| **検証用サンプル3本の作成**（いちばん使う） | D-21 |
| 疎通確認のリハーサル | D-7 |
| 当日のトラブルシュート（参加者の症状を手元で再現する） | 当日 |
| デモ・講評の準備 | 当日 |

**分ける最大の理由はコスト比較を汚さないこと。** チーム別の使用量を講評で見せるなら、そこに運営の利用（合宿前から発生する）が混ざると比較が成立しない。

副次的に、運営の利用がチームの spend limit を食わない／チームのキーを配る前から使える／失効タイミングを分けられる、という利点がある。

> 運営メンバーがチームにも参加する場合は、両方のキーを持って使い分ける。チームの開発はチームのキー、サンプル作成とトラブルシュートは運営のキー。`.env` を切り替えるだけの手間で、比較の数字が守れる。

**この構成は Corp Eng の「統一的に管理」という方針と両立する。** ワークスペースは Organization 配下の管理単位そのものであり、既存の管理体系から外れた抜け道を作るものではない。合宿後にワークスペースごと畳めるため、継続管理の負担も残らない。

- 各チームには、そのチームのワークスペースのキーを1本配る
- **キーはチーム内で共有する**（3〜4名が同じキーを使う）
- チームをまたいだキーの共有はしない
- 合宿終了後、全キーを失効させる

### 要件との対応

| 要件 | どう満たすか |
| --- | --- |
| 同じ環境で動く | 全チームが同一の組織・同一モデルを使う |
| 費用の上限 | **ワークスペース単位の spend limit** で技術的に強制 |
| チーム別の可視化 | ワークスペース単位で使用量が集計される |
| 準備の手間 | Console でワークスペースを作るだけ（15分程度） |
| データの管理下 | 個人契約を経由しない |
| 既存ガバナンスとの整合 | 既存 Organization 配下に置き、Corp Eng の管理下で運用する |

## 検討した選択肢

### 案0: 既存の Max 座席だけで済ませる（API を使わない）

**内容:** 参加者は既に持っている法人テナントの Max 座席で Claude Code を使い、それだけで合宿をやる。API キーもクレジットも用意しない。

**却下。ただし却下の理由はコストではない。** 追加費用 $0・準備ゼロ・Corp Eng への依頼も不要で、そこは全案の中で最も優れている。**却下するのは、合宿でやりたいことが変わってしまうからである。**

- ⭕️ **追加費用ゼロ。** 座席は既に払っている
- ⭕️ **スケジュールリスクが消える。** 本 ADR 最大のリスク（承認とリードタイム）がなくなる
- ❌ **エージェントの中身が見えない。** Claude Code は完成したエージェントであり、参加者は「使う側」に留まる
- ❌ 「30行のループ」を読んで回す体験が成立しない。**学習目標そのものが失われる**
- ❌ 座席を持たない参加者（→ 論点3）は結局取り残される

**「Claude Code 活用講習」をやるなら案0で足りる。今回はそれをやらない。**

#### 派生案: Claude Agent SDK を使う

Claude Agent SDK（`@anthropic-ai/claude-agent-sdk`）は Claude Code をライブラリ化したもので、ツールを渡してエージェントを組める。Claude Code の認証をそのまま使えるため、**座席があれば API キーなしで動く可能性がある。**

**これも今回は採らない。**

- ⭕️ 座席で動くなら API クレジットが要らない
- ❌ **ループとコンテキスト管理が SDK の中にある。** 「毎回まるごと送り直している」が見えない
- ❌ ファイル読み書き・bash などの組み込みツールが最初から付いてくる。**「ツールを何にするか、description に何を書くか」という合宿の本題が薄まる**
- ❌ **座席で参加者のプログラムを動かしてよいかは未確認**（→ 論点4）

> **合宿後の本番運用ではむしろ有力。** 社内ツールを実際に作る段になれば、ループを自分で持つ理由はほとんどない。**合宿で中身を知り、本番では SDK に任せる。** それが想定している道筋である。

### 案1: 単一の共用 API キーを全員で使う

**内容:** 組織アカウントのキーを1本作り、25名全員に配る。

**却下。** 要件を満たすが、上限と可視化が効かない。

- ❌ 1チームが暴走すると全体の残高が尽きる。**他チームを巻き込む**
- ❌ 誰がいくら使ったか分からない
- ❌ キーが漏れたときの影響範囲が全体に及ぶ
- ⭕️ 「みんな同じ環境」という狙いは満たす

> **利用規約上の懸念について**
> 当初「キーの使い回しは規約違反ではないか」という懸念があった。整理すると、**API キーは座席（seat）ではなく組織が所有する認証情報**であり、per-seat 課金の Pro / Max プランとは性質が異なる。Console に **Workspaces**（ワークスペースごとに鍵と上限を持つ機能）が用意されていること自体、チーム単位で配る運用が想定されていることを示す。
> 社内の業務で組織アカウントのキーを配布すること自体は通常の使い方と考えられるが、**正式な確認が必要なら利用規約の原文および法務に確認する**（→ 未解決の論点2）。

### 案2: 組織アカウント + ワークスペース分割 ← **採用**

案1の利点を保ったまま、上限と可視化を追加したもの。詳細は「決定」の項。

### 案3: 参加者が個人でクレジットを購入し、後日経費精算する

**却下。** 運用負荷とガバナンスの両方で劣る。**加えて、会社の方針に逆行する。**

> カミナシは個人が Claude Max を契約して経費精算する運用から、**法人テナントへの移行を既に完了させている**。個人購入＋精算モデルに戻す提案は、その意思決定を巻き戻すことになる。

- ❌ 25名が各自アカウント作成 → 購入 → 領収書 → 精算申請。**運営と経理の手間が25倍**
- ❌ 社内データの通り道が**個人契約**になる
- ❌ 中央から使用量が見えない、止められない
- ❌ 上限が「お願い」にしかならない（技術的に強制できない）
- ❌ 立て替えが発生し、精算完了まで時間がかかる

仮にこの案を採る場合の上限額は **1人 $20（約3,000円）** で足りる（根拠は後述の実測値）。ただし同じ $500 なら組織アカウントに入れるほうが良い。

### 案4: Claude Platform on AWS / Amazon Bedrock を使う

**今回は却下。** ただし合宿後の本番運用では有力。

- ❌ **トークン単価は安くならない。** 得られるのは請求と権限の一元化であって、価格ではない
- ❌ IAM ロール設計、`AWS_REGION` / `ANTHROPIC_AWS_WORKSPACE_ID` の設定、参加者への権限付与が必要
- ❌ Bedrock の場合、モデルアクセス有効化とクォータ引き上げに**リードタイム**がある
- ❌ Bedrock は機能がファーストパーティ API の部分集合（Managed Agents 非対応など）
- ⭕️ 請求が AWS に乗る／クレジット購入が不要
- ⭕️ 大規模・恒常運用なら明確に有利

**この規模（6チーム・2日間）では、削減できる管理コストより構築コストのほうが大きい。** Console でワークスペースを6個作るのは15分で済む。

## 費用の根拠

### 実測値

テンプレートのエージェント（社内資料を検索して答えるもの）を実際に動かした結果。

| 実行内容 | 周回数 | コスト |
| --- | --- | --- |
| 「経費精算の締め切りは?」 | 3周 | $0.031 |
| 同上（別実行） | 3周 | $0.048 |
| 保存を拒否して会話継続 | 5周 | $0.097 |

**1回あたり $0.03〜0.10、平均 $0.06 程度。**

### 試算

| | 計算 | 金額 |
| --- | --- | --- |
| 1チームが2日間で 300 回叩く | 300 × $0.06 | $18 |
| 1チームが2日間で 500 回叩く | 500 × $0.06 | $30 |
| **6チーム分** | | **$110〜180** |
| チャージ額 | | **$300** |

**$300 で十分な余裕がある。**

### 座席の追加（API クレジットとは別）

法人テナントの座席を持っていない参加者がいる場合、**座席の追加費用が別途発生する**。API クレジットとは別の財布なので、予算も別に立てる。

| 項目 | 金額 |
| --- | --- |
| 追加する座席数 | （名簿の突き合わせ後に確定） |
| 座席の単価 | （法人契約の内容による。Corp Eng に確認） |
| 小計 | **（記入する）** |

> 座席は月額課金であり、合宿の2日間だけ契約することはできない。**合宿後も継続して使うのか、期間後に外すのか**を先に決めておく。ニューカマーであれば、そのまま常設の座席にするのが自然。

## 未解決の論点

> ⚠️ **すべて Corp Eng との確認が必要。** チャージ額と実行可否がここで決まる。
> **統一管理の体制がある以上、承認プロセスとリードタイムが読めない。相談は早いほどよい。**

### 論点1: API 利用が有効になっているか ← **最重要**

Claude Team / Max（座席課金・claude.ai）と API（従量課金・Console）は**財布が別**。

> ⚠️ **エンジニアリング用テナントが整備され、全員が Max 座席を持っていても、それは API が使えることを意味しない。**
> 座席は claude.ai と Claude Code のためのもので、`messages.create()` を叩くには別途 API クレジットが要る。**ここが今回いちばん誤解されやすい。**

- [ ] 既存 Organization で **API / Console の利用が有効か**
- [ ] **API クレジットのチャージ**は誰がどう行うか（購買フロー・稟議の要否）
- [ ] ワークスペースの作成権限は誰が持つか。運営に委譲されるか、Corp Eng が代行するか

### 論点2: 合宿用ワークスペースの新設がポリシー上認められるか

「統一的に管理」という方針に対し、**2日間の一時的なワークスペースを7個作る**ことが受け入れられるかを確認する。

- [ ] 一時ワークスペースの新設が認められるか
- [ ] 命名規則・タグ・棚卸しルールなど、従うべき既定があるか
- [ ] 認められない場合の代替案を決める（下記）

**認められなかった場合の代替:**

| 代替案 | 内容 | トレードオフ |
| --- | --- | --- |
| 既存ワークスペースを1つ借りる | 合宿期間だけ spend limit を設定して使う | チーム別の可視化ができなくなる |
| チーム数を減らして枠に収める | 2〜3 ワークスペースを複数チームで共用 | 上限の粒度が粗くなる |

### 論点3: 参加者の Claude Code は何で動くか → **大半は解消。ただし全員ではない**

**API クレジットへの影響は解消した。** エンジニアの多くは法人テナントの Claude Max 座席で Claude Code を使っており、その利用は API クレジットを消費しない。

| | 金額 |
| --- | --- |
| 6チーム分のエージェント実行（実測ベース） | $110〜180 |
| API クレジットのチャージ額 | **$300**（十分な余裕あり） |

**しかし「全員が法人テナントの座席を持っている」わけではない。** 以下のケースが確認されている。

- ジョブファミリーはエンジニアリングだが、**法人テナントを使わず個人の Pro / Max プランで利用している**人がいる（私用と業務を意図的に分けているケース）
- **合宿に参加するニューカマー**がいる。参加時点で法人テナントに入っているとは限らない
- そもそも Claude Code を使っていない人もいる

したがって、**参加者名簿と座席の突き合わせが必要**になる。

#### 参加者の状態別の対応

| 参加者の状態 | 対応 | 期限 |
| --- | --- | --- |
| **法人テナントの座席あり** | 対応不要 | — |
| **個人プランで利用中** | 合宿期間中は法人テナントの座席を用意し、そちらを使ってもらう | D-14 |
| **Claude 未利用（ニューカマー含む）** | 法人テナントに座席を追加。事前に軽く触ってもらう時間を確保 | D-14 |
| **座席が用意できなかった** | **API キーのみで参加**（下記フォールバック） | 当日 |

> **個人プランのまま業務に使うのは避ける。**
> 合宿の題材によっては社内資料を扱う。**社内データの通り道が個人契約になる**のは、法人テナントへ移行した意思決定に反する。本人が私用と業務を分けたい場合こそ、業務側は法人テナントに寄せるのが筋。

#### 前提: ニューカマーは通常フローで解決する

合宿に参加するニューカマーは、**スポット利用ではなく恒常的に使う**ことになる見込み。ジョイン時に所属チームの EM が通常の申請を出すため、**合宿の時点で Max 座席に入っている前提で動いてよい**。

合宿のための特別な手配は不要。**ただし申請が合宿に間に合うかだけは逆算して確認する。**

#### 座席が用意できなかった場合の選択肢

| 案 | 内容 | 追加コスト | 環境の揃い方 |
| --- | --- | --- | --- |
| **A. Claude Code を API キーで動かす** | 座席の代わりに API キーで認証させる | **$20〜50 / 人日** | ◎ ほぼ同じ |
| B. API キーのみ（Claude Code なし） | テンプレートは動く。手で書く | なし | △ 開発速度に差 |
| C. ペアプロにする | 座席持ちと画面共有で組む | なし | ○ 見て学べる |
| D. チーム内で役割を分ける | ツール設計・プロンプト・デモ準備を担当 | なし | ○ 別の角度で参加 |

##### 案A: Claude Code を API キーで動かす ← **少人数ならこれが本命**

Claude Code は座席（サブスクリプション）ではなく **API キーでも認証できる**。座席が用意できない人には、API キーを渡して Claude Code を動かしてもらう。

- ⭕️ **環境がほぼ揃う。** 座席持ちと同じ道具で参加できる
- ❌ **API クレジットを消費する。** Claude Code の利用は1人1日 $20〜50 と、エージェント本体より1桁多い
- ⭕️ **その人専用のワークスペースを切れば、暴走してもチームの枠を食わない**

**人数が少なければ、座席を待つよりこちらが速くて安い。**

| 対象人数 | 2日間の追加コスト | チャージ額の目安 |
| --- | --- | --- |
| 1人 | $40〜100 | $300 のまま |
| 2人 | $80〜200 | **$500 に増額** |
| 3人以上 | $120〜300 | 座席追加と比較して安いほうを選ぶ |

> **必ず専用ワークスペースを切ること。** チームの共有キーで Claude Code を動かすと、その人の利用がチームの spend limit を食い尽くし、**チーム全体が止まる**。
>
> **設定は事前に済ませる。** Claude Code に API キーを使わせる設定は当日やると詰まる。**D-7 のリハーサルで運営が実際に通しておく。**

##### 案B〜D: コストをかけない選択肢

**テンプレートは API キーだけで動く。** Claude Code は開発を速くするツールであって必須ではないため、案B でも合宿は成立する。

案C・D は、コストゼロで**学習効果はむしろ高い**場合がある。合宿の目的が「作れるという感覚を得ること」なら、ツールの description を書く・ツールを何にするか決める・デモを組み立てるといった作業は、コードを打つのと同じかそれ以上に本質に触れる（→ [作る順番](../05-reference.md) の「8割は普通のプログラミング」の残り2割がここ）。

> **どの案を採る場合も、座席のない人を単独チームにしない。** 座席を持つメンバーと同じチームに入れる。

##### 選び方

- **直前に1〜2人だけ発覚** → 案A。予算を少し積んで環境を揃える
- **3人以上** → 座席の追加と案Aのコストを比較する
- **当日になって発覚** → 案C または D。その場で凌げる

#### 確認事項

- [ ] 参加者名簿を確定し、**法人テナントの座席の有無を1人ずつ突き合わせる**
- [ ] 座席が必要な人数を確定し、Corp Eng に追加を依頼する（**リードタイムを要確認**）
- [ ] 座席追加の費用を予算に計上する（→ 費用の根拠「座席の追加」）
- [ ] ニューカマーの参加確定時期を確認する。**SSO テナントへの追加が合宿に間に合うか**を逆算する
- [ ] Claude Code 未経験者向けに、事前に触ってもらう案内を出す
- [ ] **案A に備え、Claude Code を API キーで動かす手順を D-7 のリハーサルで確認しておく**

---

### 論点4: キー共有の可否 → **Anthropic 規約側は解消済み。残るは社内ポリシー**

#### Anthropic の規約（2026-08-26 時点の公開版を確認）

**チーム内でのキー共有は、規約に抵触しないと読める。**

| 根拠 | 内容 |
| --- | --- |
| Customer の定義 | *"you or the organization, company, or other entity that you represent"* — **契約主体は組織**であり個人ではない |
| D.4 使用制限 | 禁じているのは競合製品の構築・リバースエンジニアリング・**再販**。社員間の共有への言及なし |
| D.5 責任範囲 | *"Customer is responsible for all activity under its account."* — **組織が全活動の責任を負う**建て付け。個人ごとの credential を要求していない |
| Usage Policy | 禁止されるのは対応地域外への提供・BAN 回避のためのアクセス供与。社内共有とは無関係 |

**Claude Team / Pro とは製品が違う。** それらは座席課金（per-seat）なので1座席の共有は想定外だが、**API は従量課金で、キーは座席ではなくインフラの認証情報**である。同じ直感を持ち込むと判断を誤る。

#### ただし D.5 から導かれる実務上の要請

「組織が全活動の責任を負う」ということは、**誰が何をしたか追えないこと自体がガバナンス上の弱点**になるということでもある。

**チームごとにワークスペースを分ける本案は、規約回避のためではなく、責任範囲を追跡可能な単位に絞るための設計として正当化できる。** Corp Eng への説明はこの筋で行う。

#### 残る確認事項

- [ ] **カミナシの社内ポリシーで、キーの共有が認められるか**（統一管理の体制がある以上、既定がある可能性が高い）
- [ ] **Max 座席で、参加者が書いたプログラムを動かしてよいか**（→ 案0の派生案）。今回は採らない前提だが、**当日「座席でも動かせた」と気づく人が出る**。方針として答えを持っておく
- [ ] キーの発行単位に関する社内規定（個人単位 / チーム単位 / システム単位）の有無
- [ ] 上記の規約解釈について、必要なら法務の確認を取る

> この調査は公開されている規約を読んだ結果であり、法務判断ではない。社内で正式な確認が要る場合は法務へ。

## 決定した場合にやること

### 最初にやること（今すぐ・承認の前）

- [ ] **Corp Eng に相談する。** 上の未解決の論点1〜4をまとめて持ち込む
- [ ] 承認プロセスとリードタイムを確認し、逆算して合宿日程が成立するかを判断する

> **ここが最大のスケジュールリスク。** 統一管理の体制がある以上、ワークスペース新設もクレジット購入も運営の一存では動かせない。**他のどの準備より先に着手する。**

### 運営（合宿の 4 週間前まで）

- [ ] Corp Eng と合意した構成で、既存 Organization 配下にワークスペースを 7 個用意する（チーム 6 + 運営 1）
- [ ] **API クレジット**を $300 チャージする（※ Claude Team の座席課金とは別会計。混同しやすい）
- [ ] **各ワークスペースに spend limit $50 を設定する**
- [ ] 命名規則・棚卸しルールなど、Corp Eng の既定に従っているか確認してもらう
- [ ] **参加者名簿と法人テナントの座席を突き合わせ、不足分の追加を依頼する**
- [ ] ニューカマーの SSO テナント追加が合宿に間に合うかを確認する

> ⚠️ **spend limit の設定を忘れると当日詰まる。** 組織に残高があっても、ワークスペース側の上限が未設定・$0 だと `400 Your credit balance is too low` が返る。**キーが正しくても落ちる**ため、原因に気づきにくい。

### 運営（1 週間前まで）

- [ ] 各ワークスペースの API キーを発行し、チームリーダーに配布する
- [ ] 運営自身が参加者と同じ手順で疎通確認を通す
- [ ] 参加者に前日までの疎通確認を依頼する

### 合宿後（1 週間以内）

- [ ] 全 API キーを失効させ、合宿用ワークスペースを畳む（Corp Eng の棚卸しルールに従う）
- [ ] ワークスペース別の使用量を集計する（ふりかえり資料に使う）
- [ ] 実測コストを記録し、次回の見積もり根拠にする

## 影響・結果

### 良くなること

- **チームごとのコスト比較ができる。** 「A班 $8 / B班 $40」は講評で使える材料になる。設計の効率がそのまま数字に出る
- 1チームが暴走しても、他チームは影響を受けない
- キーの失効がワークスペース単位でできる
- 参加者は `.env` にキーを貼るだけで始められる

### 受け入れるトレードオフ

- **チーム内では個人別の使用量が分からない。** 3〜4名が同じキーを使うため。今回は個人を追う必要がないので許容する
- **Corp Eng の承認とリードタイムに依存する。** 運営の一存で進められない
- 座席を持たない参加者の手配が必要になる。**API クレジットとは別の予算・別のリードタイム**
- 合宿用ワークスペースの管理者を運営側に1名立てる必要がある（権限が委譲される場合）
- 合宿後のキー失効という後片付けが発生する（→ チェックリストに記載済み）
