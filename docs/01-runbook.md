# AIエージェント合宿ランブック

社内の開発合宿で「AIエージェントを作る」をテーマにするための、運営側の準備一式。先に運営が作る検証用サンプル3本、プラットフォームの選び方、時系列の準備チェックリスト、参加者に配るテンプレートの設計方針をまとめた。

---

## 1. 検証用サンプル3本

「面白いアプリを3つ作る」ではなく、**運営リスクを1本ずつ潰すために3つ作る**。単発呼び出し → ツールループ → 外部への書き込み、と副作用の大きさで段階を上げる。この順で作ると、当日どこで事故が起きるかが先に分かる。

### A / 単発呼び出し — 議事録タスク抽出

議事録のテキストを渡すと、担当者・期限・タスク内容を構造化JSONで返す。ループなし、ツールなし、API 1回。

| 項目 | 内容 |
| --- | --- |
| 検証したいこと | 認証が通るか。モデルIDが正しいか。1リクエストの所要時間とコストの実測値。社内ネットワークから叩けるか |
| 使う機能 | Messages API + Structured Outputs（`output_config.format`） |
| 実装規模 | 100行未満 / 半日 |
| 合宿での位置づけ | 参加者が最初の30分で通す「疎通確認」そのもの。テンプレートに同梱する |

### B / ツールループ — 社内ドキュメント調査エージェント

質問を投げると、ファイル検索・ファイル読み込み・Web検索の3ツールを自分で選んで回り、根拠つきで答える。ここが「エージェント」の本体で、合宿の大半のチームはこの形に着地する。

| 項目 | 内容 |
| --- | --- |
| 検証したいこと | 1タスクあたり何ターン回って何トークン使うか。ツールが失敗したときに止まるか暴走するか。サーバーサイドWeb検索が選んだ基盤で使えるか |
| 使う機能 | Tool Use（Tool Runner もしくは手書きループ）、Web検索ツール、プロンプトキャッシュ |
| 実装規模 | 200〜300行 / 1〜2日 |
| 合宿での位置づけ | 参考実装として別リポジトリで配る。テンプレートには入れない |

### C / 副作用あり — Issueトリアージ＆通知

GitHubのIssueを読み、緊急度を判断してラベルを付け、Slackに投げる。**外部システムに書き込む**のがポイント。運営として一番怖いのはここ。

| 項目 | 内容 |
| --- | --- |
| 検証したいこと | SaaSのトークンをどうチームに配るか。人間の承認ゲートをどこに置くか。暴走したときの被害範囲。事故ったときに誰がどう止めるか |
| 使う機能 | Tool Use + 外部API + 実行前の承認フック |
| 実装規模 | 300行前後 / 1〜2日 |
| 合宿での位置づけ | これを作ると「サンドボックス用のSlackワークスペースとGitHub Orgを用意すべきか」の答えが出る。ほぼ確実に「用意すべき」になる |

> ⚠️ **落とし穴** — Cを本番のSlackやGitHubに向けたまま合宿をやると、誰かが必ずループを止め損ねて数十件〜数百件の書き込みをする。事故ではなく、ほぼ前提として起きる。専用ワークスペースを切るか、書き込み系ツールをドライラン固定にしたラッパーを配るかを先に決めておく。

## 2. 基盤の選定

「会社でやる」以上、個人のAPIキーとローカルLLMでは通らない。課金・権限・データの3点をどこで担保するかで選択肢が決まる。

| 選択肢 | 課金・権限 | 機能の範囲 | 準備の重さ |
| --- | --- | --- | --- |
| **Claude Platform on AWS** | AWS IAM + Marketplace課金。会社のAWSアカウントに乗る | Anthropic運営なので第一党APIと同等。モデルIDは `claude-opus-5` のまま | 中。`AWS_REGION` と `ANTHROPIC_AWS_WORKSPACE_ID` の2つが必須 |
| **Amazon Bedrock** | AWS IAM + AWS課金。既存のBedrock運用に乗る | AWS運営のため機能は部分集合。モデルIDは `anthropic.claude-opus-5`。Managed Agents は非対応 | 重。モデルアクセス有効化とクォータ引き上げにリードタイムあり |
| **Anthropic API 直** | 組織アカウント + 会社カード。ワークスペースでチーム分離 | 全機能。最新機能が最速で来る | 軽。1日で用意できる |
| **ローカルLLM** | 課金なし | ツール呼び出しの精度が実用に届かないことが多い | 軽いが、各自のマシンスペックに依存して当日ばらつく |

> ✅ **推奨** — すでに会社でAWSを使っているなら **Claude Platform on AWS**。IAMでチームごとに権限を切れて課金はAWSに乗り、それでいて機能制限がない。Bedrockを選ぶ理由は「既存のBedrock運用・監査体制にどうしても揃える必要がある」場合に限る。AWSを使っていない、あるいは時間がないなら Anthropic API 直で組織アカウントを取るのが一番速い。

> ⚠️ **落とし穴 1** — **Bedrockを選ぶと使える機能が減る。** サーバーサイドのWeb検索やコード実行などは基盤ごとに可用性が違い、Managed Agents（サーバー側でエージェントループとサンドボックスを回す方式）はBedrockでは使えない。サンプルBを作る段階でこれに当たるので、先に3本作る意味がここにある。

> ⚠️ **落とし穴 2** — **クォータは初期値のままだと足りない。** 6チームが同時にエージェントループを回すと、デフォルトのTPM/RPMではすぐ429が出る。引き上げ申請には日数がかかるので、遅くともD-14には出しておく。

## 3. 準備チェックリスト

日付は合宿初日を D-0 とした逆算。順序に意味があるのは、前工程の結果が次の判断材料になるため（サンプルを作らないとクォータの必要量が決まらない、など）。

### D-28（1ヶ月前）— 基盤を決めて申請を出す

- [ ] 基盤を1つに決める（上の表で判断）。複数用意しない、サポートが割れる
- [ ] 会社のアカウント・組織を作成し、課金手段を通す
- [ ] Bedrockの場合：使うモデルの「モデルアクセス」を有効化。リージョンも確定させる
- [ ] クォータ引き上げ申請を出す（想定人数 × 同時実行を根拠として添える）
- [ ] 情報システム／セキュリティ部門に一報。「社内データを外部LLMに投げるか」の可否を先に確定させる
- [ ] 予算枠を確保し、承認を取る

### D-21（3週間前）— サンプル3本を作る

- [ ] サンプルA（単発）を作り、疎通・レイテンシ・単価を実測
- [ ] サンプルB（ループ）を作り、1タスクあたりのトークン数とコストを実測 ← 予算見積もりの根拠
- [ ] サンプルC（副作用）を作り、外部SaaS連携の運用ルールを決める
- [ ] 実測値をもとに、必要クォータと予算を再計算。足りなければ申請を追加
- [ ] 選んだ基盤で「使えない機能」の一覧を作り、参加者向けに明記する

### D-14（2週間前）— 権限・コスト・環境

- [ ] チーム単位のIAMロールまたはワークスペースを作成し、キーの配布方法を決める
- [ ] **各ワークスペースの spend limit を明示的に設定する**（組織に残高があっても、ワークスペース側の上限で 400 になる）
- [ ] コスト可視化：チームごとにタグ／ワークスペースを分け、日次で見られるようにする
- [ ] 予算アラートを設定（AWS Budgets、またはワークスペースのリミット）。閾値を超えたときに誰が何をするかまで決める
- [ ] テンプレートリポジトリを作成（内容は §5）
- [ ] 参考実装リポジトリ（サンプルB・C）を公開
- [ ] お題リストと審査基準を確定

### D-7（1週間前）— リハーサルと事前配布

- [ ] **運営の1人が、参加者と同じ手順で、素の環境から疎通まで通す。**ここを飛ばすと当日必ず詰まる
- [ ] **残高を2箇所とも確認**（どちらが欠けても 400 で落ちる。キーが正しくても通らない）
  - 組織のクレジット残高（※Claude Pro / Max のプラン購入とは別会計。API クレジットを買うこと）
  - 配布する**各ワークスペース**の spend limit
- [ ] 会社のプロキシ／ファイアウォール越しにAPIが叩けるか確認
- [ ] 合宿会場の回線を確認。帯域と、社内VPNが必要かどうか
- [ ] 参加者にキーとリポジトリを事前配布し、**前日までに疎通確認を済ませてもらう**
- [ ] チーム分けを確定して通知
- [ ] タイムテーブルと審査基準を配布

### D-1（前日）— 最終確認

- [ ] 全員の疎通確認が取れているか集計。取れていない人を個別にフォロー
- [ ] キーが失効していないか、クォータが反映されているかを再確認
- [ ] オフライン用の予備：モバイルルーター、電源タップ、予備キー
- [ ] 質問対応の当番と連絡先（Slackチャンネル）を決める

### D-0（当日）— 進行

- [ ] 冒頭15分で全員の疎通を確認してから、お題発表に進む
- [ ] コスト消費を数時間おきにチェック。異常なチームがあれば早めに声をかける
- [ ] 中間チェックポイントを1回入れる（「動くものが1つでもあるか」だけを見る）
- [ ] デモは実機で。スライドだけの発表は認めない、と先に言っておく

### D+7（事後）— 片付けと回収

- [ ] キー・IAMロールを失効させる（一番忘れられる工程）
- [ ] サンドボックス用のSlack／GitHubを整理
- [ ] 実際にかかったコストを集計し、次回の見積もり根拠にする
- [ ] 詰まった箇所を集めてテンプレートのREADMEに反映

## 4. コスト見積もり

下はAnthropic第一党APIの参考単価（100万トークンあたり）。BedrockとVertex AIはパートナー運営で別価格になるので、選定後にそちらの価格表で引き直す。

| モデル | モデルID | 入力 $/1M | 出力 $/1M | 合宿での使いどころ |
| --- | --- | --- | --- | --- |
| Claude Opus 5 | `claude-opus-5` | $5.00 | $25.00 | エージェント本体。判断の質が要るところ |
| Claude Sonnet 5 | `claude-sonnet-5` | $3.00 | $15.00 | コスト重視の周辺処理 |
| Claude Haiku 4.5 | `claude-haiku-4-5` | $1.00 | $5.00 | 分類・要約などのサブタスク |

### 財布は2つある（ここを混ぜると事故る）

| 財布 | 何に使うか | 課金 |
| --- | --- | --- |
| **Claude のプラン（Pro / Max）** | 参加者が使う Claude Code、claude.ai | 席数×月額。**API では1円も使えない** |
| **API クレジット** | 参加者が作ったエージェントの `messages.create()` | 従量。Console で別途購入 |

**この2つは完全に別会計です。** プランをいくら上げても API は動きません。逆に API クレジットを積んでも Claude Code の利用枠は増えません。

「Claude Code が使えているのに、自分のコードから叩くと 400 が返る」は**必ず起きる**ので、D-7 のリハーサルで踏んでおくこと。

### 枠の取り方

**① Claude Code 側** ── 参加者が既に Max などの席を持っているなら追加費用はゼロ。持っていない人がいる場合だけ、当日分の席を手当てする。

**② API クレジット側** ── 参加者のエージェントが実際に消費する分。エージェント開発中は1タスク数セント〜数十セント程度なので、**1人1日 $5〜15** をみておけば足りることが多い。18人×2日なら $200〜550、予備込みで **$1,000 程度**。

ただしこれは概算であって、**正確な根拠はサンプルBの実測から取る**。D-21でサンプルを作る目的の半分はこの数字を取ることにある。

> **Claude Platform on AWS / Bedrock を使う場合は、②のクレジット購入は不要。** AWS の請求に乗るので、この財布の分裂自体が起きない。基盤選定でこちらを勧めている理由のひとつでもある。

> 💡 **コストを下げる打ち手** — プロンプトキャッシュを効かせると入力側が大きく下がる（キャッシュ読み出しは通常入力の1割）。テンプレートに最初から仕込んでおくと、参加者が意識しなくても効く。加えて、毎リクエストのトークン数とコストをログに出す仕組みをテンプレートに入れておくと、参加者にコスト感覚が身につき、運営側も集計しやすくなる。

## 5. テンプレート戦略

結論から言うと、**「薄いテンプレート」＋「参考実装」＋「お題リスト」の3点セット**を配る。フルスクラッチも分厚いフレームワークも、どちらも失敗する。

### なぜ両極端が失敗するか

**完全に自由にすると**、初日の午前が環境構築とネタ決めで溶ける。認証周りで詰まるチームが必ず出て、成果物ゼロで終わる班が発生する。

**分厚いフレームワークを配ると**、今度はそのフレームワークの読解に時間が溶ける。しかも参加者が「エージェントのループを自分で書く」経験をしないまま終わるので、合宿の狙いから外れる。エージェントのループはそんなに難しくないし、そこが一番学びになる部分でもある。

### 配るもの・配らないもの

**テンプレートに入れる**

- 15分で疎通するまでの手順だけを書いたREADME
- ロック済みの依存（`uv.lock` / `package-lock.json`）
- `.env.example` と認証確認スクリプト
- 50行程度の最小ツール呼び出しループ 1本
- トークン数とコストを毎回出力するロガー
- devcontainer（用意できるなら）

**入れない**

- 抽象化された `BaseAgent` クラス
- プラグイン機構・DIコンテナ
- サンプルB・Cのコード本体
- UIフレームワークの選定
- 「正しいアーキテクチャ」の型

サンプルB・Cは**テンプレートとは別のリポジトリ**に置き、「読んで真似していい参考実装」として案内する。テンプレートに混ぜると、参加者はそれを消すところから始めることになる。

### お題の出し方

完全自由だとネタ決めで半日溶けるので、**お題カテゴリを4つほど提示して選ばせる＋自由枠も残す**のがちょうどいい。カテゴリの例：

1. 社内の定型業務を1つ自動化する（申請、集計、レビュー依頼）
2. 散らばった情報を横断して答えるエージェント（Wiki、Slack、コード）
3. 開発フローに割り込むエージェント（PRレビュー、テスト生成、障害の一次調査）
4. マルチエージェント：役割の違うエージェントを協調させる
5. 自由枠

### 審査基準は先に配る

これを事前に言わないと、全チームが設計に凝って動かないまま終わる。**「動くこと ＞ きれいなこと」**を明示する。基準の例：

- 実機でデモが通ること（必須条件。ここを最優先だと明言する）
- エージェントらしさ：判断とツール選択をモデルに任せているか。if文の羅列は評価しない
- 実用性：明日から誰かが使いたいと思うか
- 学び：うまくいかなかったことの共有も加点対象にする

## 6. 落とし穴

当日詰まる原因になりやすいものを、影響の大きい順に。

| いつ効いてくるか | 内容 | 対策 |
| --- | --- | --- |
| 当日、開始30分 | クォータ不足で429が出る | D-14までに引き上げ申請。同時実行数を根拠に添える |
| 当日、開始30分 | **残高不足で 400 が返る** | D-7に確認。キーが正しくても落ちるので原因に気づきにくい。組織のクレジット残高と、**ワークスペースごとの spend limit** の両方を見る |
| 当日、開始30分 | 社内プロキシ／FWでAPIに到達しない | D-7に運営が実機で確認。会場の回線でも試す |
| 当日、開始30分 | 環境構築でつまずく人が出る | 依存をロックし、前日までに全員の疎通確認を取る |
| 設計時点 | 基盤を決めた後で「その機能が使えない」と分かる | サンプル3本を先に作る。特にBで機能可用性を洗う |
| 開発中 | エージェントが無限ループしてコストが跳ねる | 最大ターン数の上限をテンプレートに固定で入れる。予算アラートを設定 |
| デモ時 | 本番のSlack／GitHubに大量書き込み | サンドボックス環境を用意。書き込み系は承認ゲートを通す |
| 合宿後 | キーが失効されずに残る | D+7の片付けをチェックリストに載せ、担当者を決めておく |
