# ハンズオン ── Day 1 の朝、45分

> **これがレベル合わせの本体です。** 事前に何も読んでいない人も、この45分で全員同じ場所に立ちます。
> 事前資料を読んできた人にはおさらいになりますが、飛ばさせないでください。**環境が壊れている人をここで見つける**のが半分の目的です。

| | 時間 | やること | 手を動かすのは |
| --- | --- | --- | --- |
| 1 | 15分 | ループの説明を聞く（[これだけ](00-tldr.md) を投影） | 運営 |
| 2 | 10分 | 自分の手元で1回動かす | 全員 |
| 3 | 20分 | ツールを1個足して、呼ばれないのを見て、直す | 全員 |

終わったら「よーいドン」です。

---

## 1. ループの説明 ── 15分

運営が [これだけ](00-tldr.md) を投影しながら話します。**参加者は手を止めて聞いてください。**

`src/agent.ts` を開いて、30行のループを上から順に指でなぞるのがいちばん速いです。伝えるのは4つだけ。

1. ループが1周するたびに、**これまでの全部**をもう一度送っている
2. モデルは「このツールを呼べ」と言うだけで、**呼ぶのはこちらのコード**
3. だから承認ゲートもログもコスト計測も、全部この1箇所に入る
4. 参加者が書くのは `src/tools.ts` の3つだけ（`SYSTEM_PROMPT` / `tools` / `runTool`）

> **運営向け** — ここで質問を取り始めると必ず溢れます。「質問は3のあとで」と先に言ってください。
> 説明が刺さらなくても構いません。3で手を動かせば分かります。

## 2. 動かす ── 10分

**ここで詰まった人は手を挙げてください。** 全員が通るまで先に進みません。

```bash
bun install
cp env.example .env        # 運営から配られたキーを貼る
bun run check              # 疎通確認
```

`bun run check` が通ったら、エージェントを1回動かします。

```bash
bun run agent "今日は何日?" -v
```

`-v` は、モデルが何を考えて次のツールを選んだかを表示するオプションです。

**出力のここを見てください。**

```
  [1周目] in 1,234 / out 89 / 累計 $0.0028      ← 1周ごとのトークンとコスト
  [考え中] 現在時刻が必要なのでツールを使う      ← -v で出る
  → get_current_time({})                        ← モデルが「呼べ」と言い、こちらが実行した
  [2周目] in 1,410 / out 45 / 累計 $0.0041      ← 入力が増えている＝全履歴を再送している
```

**2周目の入力トークンが1周目より増えているのが見えますか。** これが「毎回まるごと送り直している」ということです。

> **運営向け** — ここで出るトラブルは、ほぼ全部この3つです。
>
> | 症状 | 原因 |
> | --- | --- |
> | `✗ 認証情報が見つかりません` | `.env` を作っていない／キーを貼っていない |
> | `400 credit balance` | 残高かワークスペースの spend limit。運営側の問題 |
> | ネットワークに届かない | 会場の回線・プロキシ。前日に実機で確認しておくこと |

## 3. ツールを1個足す ── 20分

合宿の2日間、参加者がやり続けるのはこの作業です。**先に1回、全員でやります。**

### 3-1. わざと雑な説明で足す（10分）

`src/tools.ts` を開いて、2箇所に足します。

**① 名簿（`tools` 配列）に追加**

```ts
  {
    name: "days_until",
    description: "日数を計算する",          // ← わざと雑にしてあります
    input_schema: {
      type: "object",
      properties: {
        date: { type: "string" },
      },
      required: ["date"],
    },
  },
```

**② 中身（`dispatch` の `switch`）に追加**

```ts
    case "days_until": {
      const target = new Date(args.date ?? "");
      if (Number.isNaN(target.getTime())) {
        return `日付を解釈できませんでした: ${args.date}`;
      }
      const days = Math.ceil((target.getTime() - Date.now()) / 86_400_000);
      return `${args.date} まで あと ${days} 日`;
    }
```

動かします。

```bash
bun run agent "今年の大晦日まであと何日?" -v
```

**何が起きたかをメモしてください。** チームによって違うものが見えるはずです。

- そもそも `days_until` を呼んだか、呼ばなかったか
- `get_current_time` を先に呼んで今日の日付を確かめたか、確かめずに推測したか
- `date` に何を渡してきたか（`2026-12-31` か、`今年の大晦日` か、`2026年12月31日` か）
- エラーが返ったあと、自力で直したか、同じことを繰り返したか

> **運営向け** — ここは**うまくいかないのが正解**です。「動かない」と手が挙がったら成功なので、そう伝えてください。
> 実行するたび結果が変わります。それ自体が「モデルがその場で順番を決めている」ということです。

### 3-2. 説明を直す（10分）

`description` を書き直します。**「何をするか」だけでなく「いつ使うか」「何を渡すか」まで書きます。**

```ts
  {
    name: "days_until",
    description:
      "指定した日付まで、今日からあと何日あるかを返す。" +
      "「あと何日」「締め切りまで」のように、未来の日付までの日数を聞かれたときに使うこと。" +
      "今日が何日か分からないときは、先に get_current_time で確認すること。",
    input_schema: {
      type: "object",
      properties: {
        date: {
          type: "string",
          description: "基準となる日付。YYYY-MM-DD 形式。例: 2026-12-31",
        },
      },
      required: ["date"],
    },
  },
```

**変えたのは説明文だけです。実装は1行も触っていません。** もう一度動かします。

```bash
bun run agent "今年の大晦日まであと何日?" -v
```

`get_current_time` → `days_until` の順に呼ぶようになったはずです。

これが今日いちばん大事な一点です。

> **モデルは、あなたが書いた説明文しか読んでいません。実装は見えていません。**
> ツールを呼んでくれないときは、まず説明文を疑ってください。

数字で見たい人は、変える前と後でこれを走らせると、平均ツール呼び出し回数が比べられます。

```bash
bun run measure "今年の大晦日まであと何日?" 5 src/cli.ts
```

## ここまで来たら、よーいドン

あとはこの繰り返しです。

1. どんなツールが要るか決める（3〜5個に絞る）
2. `tools` に名簿を書く
3. `runTool` に中身を書く ← **ただの関数。ここが作業量の大半**
4. 動かして、説明文を直す

書き方に詰まったら、動く作例が3つあります。**丸ごとコピーして、そこから壊すのが最短**です。

```bash
cp examples/doc-agent/tools.ts   src/tools.ts   # ローカルのファイルを読む
cp examples/http-agent/tools.ts  src/tools.ts   # HTTP を叩く
cp examples/state-agent/tools.ts src/tools.ts   # 状態を書き換える
```

どれがどんなときに向くかは [examples/README.md](../examples/README.md) にあります。
